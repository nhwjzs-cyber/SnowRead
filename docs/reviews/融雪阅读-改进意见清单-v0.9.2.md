## 0. 复核方法与口径

逐个通读 36 个主源文件，并按"用户动作 → 调用链 → 主线程/IO 线程 → 分配与 I/O"的方式核对关键路径；对照 `docs/specs` 的待办清单、`CHANGELOG`、`FIX-v0.9.2.md` 判断哪些已完成、哪些仍有效。

编号含义：

| 前缀 | 类别 | 说明 |
|---|---|---|
| **E** | 效率 | 同样功能下更少耗时/内存/写盘，用户可感知 |
| **B** | 正确性 | 行为与文案不一致、边界错误、易踩的设计陷阱 |
| **F** | 功能 | 建议新增或补强的能力 |
| **Q** | 工程 | 可维护性、发布、测试 |

工作量：**S** ≤ 0.5 天，**M** 0.5–2 天，**L** 3–5 天。

先说结论：**这份代码的工程质量在同类个人项目里偏上**——纯 Java 文本引擎与 Android 解耦、索引原子写、备份逐字节校验、长任务可取消且末段不可打断、零第三方依赖、无 INTERNET 权限。下面所有建议都不要求推翻这些设计，只针对"高频路径上的浪费"和"还没补的洞"。

## 1. 摘要：如果只看一页

1. 体验瓶颈已经不在功能数量，而在**三条高频路径**：写库、听书高亮、分页测量。
2. **写库在主线程 fsync**（`persist()`），滚动停止、加书签、改名都会卡一下；500 本时每次序列化百 KB 级 JSON。
3. **听书每朗读一个词**都会重建整页 `StaticLayout` 并把整个列表 `notifyDataSetChanged()`，这是听书掉帧的主因。
4. **分页每算一页都排版 8192 字**，而一页通常只有 300–600 字，约 10–20 倍无效排版；且页索引不落盘，改字号/重开书全部重算。
5. **书架、目录、搜索、面板四个列表都没有复用 `convertView`**，目录上万项时滚动成本随滚动距离线性增长。
6. 5 个 P0 合计约 5–7 人日，能清掉大部分"卡一下"的体感问题，且不改数据结构。
7. 功能上最值得补的三个洞：**内置开源宋体**（现在宋体取决于手机）、**按书独立排版记忆**、**阅读位置与文本编码解耦**。
8. 最该克制的：**继续增加管理维度**（分类层级、阅读状态、更多统计）。书架的管理成本已经接近临界点。

## 2. E 类：效率与性能

### P0（建议下一版就做）

#### E01 书库在主线程写盘并 fsync

**证据**：`MainActivity.persist():585` 直接调用 `LibraryStore.save():140-146`，后者 `metadata()` 序列化全部书籍，再经 `AtomicFile.finishWrite()` 落盘（内含 fsync）。调用点全在 UI 线程：滚动停止 `onScrollStateChanged:466`、翻页 `PagedReaderView.changed → persist:453`、退出 `leaveReader:586`、开书 `openBook:423`、排版预览 `appearance:668`，以及 `editBookmark:800`、`renameBook:866`、`organize:223`、删书签 `:634`。

**问题**：书架 500 本时，每次保存要构建 500 个 `JSONObject` + 序列化 + 写盘 + fsync，量级在百 KB / 5–20 ms。它恰好发生在"手指刚停下"的瞬间，是最容易被感知为"卡一下"的位置；听书时还会与 IO 线程争锁。

**建议**：引入单一写库通道 `LibraryWriter`：内存模型立即改，落盘走单线程 + dirty 标记 + 200–400 ms 合并窗口；`onPause` / 退出阅读 / 导入结束 / 备份前强制 flush；写失败回滚到写前快照并 toast。`LibraryStore.save()` 保持同步语义不变，只是不再由 UI 线程调用。

**收益**：消除滚动停止、加书签、改名时的主线程 fsync；写盘次数从"每次动作"降到"每次窗口"。**工作量 M。**

---

#### E02 听书每朗读一句就整库重写

**证据**：`ListenService.save(boolean):139` → `LibraryRepository.progress():33-38` → `store.save()`。`TtsEngine` 的 `onStart` 回调（`ListenService:69`）每句都调用 `save(false)`，`force=false` 只做"同时只有一个在飞"的合并，不做时间窗合并，因此实际约每句（3–6 秒）落盘一次，每次都是全量索引。

**问题**：一本 500 本的书库，听书 1 小时 ≈ 600–1000 次全量写 + fsync。耗电、闪存写放大，并且在朗读间隙可能触发 GC/IO 抖动。

**建议**：进度按"每 10 秒 或 章节切换"落盘；`pause` / `stop` / `onDestroy` / 切书强制落盘；句子粒度只更新内存中的 `Book.offset`。用 E01 的同一个写库通道，避免两套路径。

**收益**：写盘频率降一个数量级；听书长播的耗电与抖动明显下降。**工作量 S。**

---

#### E03 词级高亮触发整页重排与整个列表重绑

**证据**：`TtsEngine.onRangeStart:43` → `ListenService.range():70` → `publish(false)` → `Snapshot` + 监听器 → `MainActivity.onListeningChanged:881-886` → `refreshHighlights():580-583`：

- 分页模式：`PagedReaderView.setListenHighlight():74` → `render():167-175`，重新 `typography.style()` 整页 + 新建 `StaticLayout`；
- 滚动模式：`readerAdapter.notifyDataSetChanged()`，所有可见行重新 `getView`。

`onRangeStart` 是按词触发的（中文 TTS 约每秒 4–6 次）。

**问题**：朗读时每秒 4–6 次整页文字 shaping + 整表重绑，中低端机会直接掉帧；这正是"听书时页面发飘"的根因。

**建议**：
1. 高亮与排版分离。页内高亮改为在既有 `layout` 上叠加绘制（`canvas.drawRect` 按 `layout.getLineForOffset` 求行矩形，或用 `Drawable` 作为 `background`），不重建 `StaticLayout`；
2. 范围回调在 `ListenService` 侧合并到 100–150 ms（`rangeStart/rangeEnd` 只保留最后一次）；
3. 滚动模式只更新命中行：`reader.getChildAt(pos - getFirstVisiblePosition())` 单行重设 `Spannable`，不 `notifyDataSetChanged()`。

**收益**：听书时主线程工作量下降一个数量级，且不再与翻页动画抢帧。**工作量 M。**

---

#### E04 每算一页都排版 8192 字

**证据**：`PagedReaderView.fitPage():120-132`：

```java
int windowEnd = Math.min(limit, start + 8192);
StaticLayout measure = typography.layout(typography.style(text, start, windowEnd, ...), paint, width, spacing);
int fitted = 0;
while (fitted < measure.getLineCount() && measure.getLineTop(fitted + 1) <= height) fitted++;
```

每调用一次只取"第一屏能放下的行"，然后丢弃整个 layout；下一页重新从 `start` 起再排 8192 字。

**问题**：一页 300–600 字，却为它 shaping 8192 字，约 10–20 倍浪费。长章节（4 万字 ≈ 70 页）首次进入或深层跳转时，用户在"正在定位页面…"上等待的时间基本由这里决定。

**建议**：滑动窗口批量切页。一次 layout 覆盖 8–16 K 字后，用同一个 `StaticLayout` 连续切出多页（`getLineStart/getLineTop` 直到高度用尽），窗口耗尽再推进；`PageIndex.extend()` 的 `Fitter` 接口从"切一页"扩展为"切一批"。注意 `text.charAt(end-1)` 的代理对边界处理要保留。

**收益**：分页吞吐提升约一个数量级；长章节首次进入从秒级降到百毫秒级。**工作量 M。**

---

#### E05 四个列表都没有复用 convertView

**证据**：

| 位置 | 每次 getView |
|---|---|
| `ShelfAdapter.getView:206` | 新建 `LinearLayout` 子类 + `BookCoverView` + `ShelfTitleView` + 徽标 + 进度条，完全忽略 `reused` |
| `chapters()` 内 adapter `:592` | 新建 `LinearLayout` + `TextView`（可能还有"当前"标记） |
| `search()` 内 adapter `:646` | 新建 `LinearLayout` + 2 个 `TextView` + `SpannableString` |
| `AppSheet` 列表 `:71` | 新建 `LinearLayout` + 2 个 `TextView` |
| `manageCategories` `:252` | 新建 `SwipeActionRow` 等 |

（`ReaderAdapter:898` 是唯一正确复用了 `TextView` 的。）

**问题**：目录最多 1 万项、搜索 1000 条、书架数百本，滚动时每帧都在新建 View 树并触发 measure/layout。`ShelfAdapter` 还叠加了 `BookCoverView` 的自定义绘制，单帧成本最高。

**建议**：标准 ViewHolder 复用。书架卡片复用时需额外处理三件事：清空旧 bitmap（避免串封面）、`Motion.reset(tile)` 复位按压态、重新计算选中/置顶徽标。`ShelfTitleView` 的字号自适应结果可按 `(title, width)` 缓存，避免每次 measure 都试 5 个字号。

**收益**：目录与书架滚动帧率提升最明显，且内存分配下降（减少 GC 抖动）。**工作量 M（书架部分要仔细回归）。**

## 4. F 类：功能改进建议（不在原待办清单内的新提案）

> 已在 `docs/specs/融雪阅读-待办清单-v1.md` 列出的（导入预览、TXT 清洗、列表视图、排序、阅读状态、大文件、虚拟分章、平板双栏、自动备份、崩溃日志等）此处不重复，见 §7。

### F01 内置一款开源宋体子集（P1 / M）

**现状**：`Aa 排版` 里明确写"宋体字形由手机字体支持情况决定"，`ReaderTypography` 用 `Typeface.SERIF`。国产 ROM 上 `SERIF` 常常回落到黑体，"宋体"这个选项等于不存在。

**建议**：内置一款 OFL 授权宋体（思源宋体 / 霞鹜文楷的子集，常用 7000 字 + 标点 ≈ 3–6 MB），或提供"内置宋体（推荐）/ 系统字体"二选一。字体文件放 `assets`，启动时按需 `Typeface.createFromAsset`。

**收益**：阅读器最核心的"字"终于可控；也是与同类产品拉开差距最直接的一处。代价是 APK 体积。

### F02 按书独立记忆排版（P1 / S–M）

**现状**：字号、行距、页边距、主题、常亮全部全局共享。读网文想用小字密排、读严肃文学想用大字宽行距，只能每次手动改。

**建议**：`Book` 增加可选的 `typeset` 覆盖字段（缺省 = 跟随全局）。在"Aa 排版"顶部加一行"仅对《书名》生效"的开关。数据结构可选字段，不破坏 v3 格式与旧备份。

### F03 阅读位置与文本编码解耦（P1 / M）

**现状**：`Book.offset` 是全文 UTF-16 字符偏移；`changeEncoding` 直接把 `offset=0` 并把书签全清（`MainActivity:817`）。换一次编码 = 丢失全部进度与书签。

**建议**：
1. 持久化 `chapterIndex + charOffsetInChapter`（或"章节标题 + 章内比例"），全局 offset 只做运行时缓存；
2. 切换编码时按"章节标题 + 章内百分比"重新定位，书签用同样方式映射，映射失败的单独列出而不是整体清空；
3. 顺带解决"文本被外部替换/重新导入后进度错位"。

**收益**：把一个破坏性操作变成可逆操作；这也是后续做"备份跨版本恢复"的基础。

### F04 进度条上标书签，长按进章节跳转（P1 / S）

**现状**：书签只能在"书签"面板里看列表；进度条只是一个纯 seek。

**建议**：在 `SeekBar` 上方叠一层 2 dp 刻度条，把 `active.marks` 画成小点；点按书签点直达；长按进度条弹出"跳转章号"。成本很低，但"这本书我标过哪"变得一眼可见。

### F05 阅读手势可配置（P1 / S–M）

**现状**：只有左右 1/3 点击 + 中间唤出工具栏（`PagedReaderView:53-57`），音量键翻页需手动开。

**建议**（按性价比排序）：
1. **双指上下滑调亮度**——阅读器通用手势，不用退出阅读；
2. **双击中间区域**收藏书签；
3. 上滑/下滑翻页（可关，避免与滚动模式冲突）；
4. 音量键**长按连续翻页**（现在只处理 `repeatCount==0`，`dispatchKeyEvent:745`）。

### F06 听书：预合成下一句 + 从选中处开始（P1 / M）

**现状**：`TtsEngine.speak` 用 `QUEUE_FLUSH`，每句都要等引擎起播，句间有 300–800 ms 空白；听书起点只能是"当前页/本章/全书"。

**建议**：
1. 当前句播放时，用 `synthesizeToFile` 预生成下一句到 `cacheDir`，`onDone` 后直接 `playFromFile`（不支持时静默回退到现状）；
2. 长按正文选段 → "从这段开始朗读"，把 `SCOPE` 的 `offset` 设为选区起点。

### F07 导入时清洗书名与编码打分（P1 / M）

**现状**：书名直接取文件名，常见 `[完结]《xxx》(1-1000章)作者：yyy.txt` 原样进书架（`ShelfTitleView` 只能靠缩小字号硬塞）。编码只在 UTF-8 失败时盲选 GB18030（`TextDocument.decode:177-178`），Big5 文件会静默变乱码。

**建议**：
1. 书名清洗规则：去扩展名、去 `【】[]()` 包裹的站点/状态/章数、去 `作者：` 后缀、压缩空白；提供"恢复为文件名"；
2. 编码打分：GB18030 与 Big5 都能"解码成功"，用常用字命中率 + 生僻字/替换率打分择优，并在导入预览里显示"检测：GB18030（置信度高）"。

### F08 书架规模化：索引条 + 自定义排序（P2 / M）

**现状**：`ShelfOrganization.visible` 只按"置顶 → 最近打开"排序，无自定义顺序；500 本时只能靠搜索。

**建议**：
1. 右侧 A–Z / 拼音首字母索引条（中文取首字母）；
2. 长按拖动排序（写入 `order` 字段，缺省回落到最近打开）；
3. 多选后支持"批量导出 TXT / 批量移入回收站"（现在批量只有置顶与分类）。

### F09 搜索增强（P2 / S–M）

**现状**：`SearchResults.find` 是大小写敏感的 `indexOf`，全量扫描，结果平铺 1000 条。

**建议**：英文忽略大小写（`regionMatches(true,…)` 保 offset 映射）；结果按章节分组折叠；"仅本章内查找"；搜索历史（最近 10 条）。跨书搜索仍建议延后到有索引方案时。

### F10 EPUB 支持（战略选项 / L）

**说明**：这是唯一能显著扩大受众的功能，但也是唯一会动摇"纯 TXT + 极简"定位的功能。最小可行路径：ZIP 解包 → 解析 `container.xml` / `.opf` / spine → 把 XHTML 转纯文本段落后复用 `TextDocument` 的分章与分页（图片暂不支持，只取封面）。**建议先做产品决策，不排期**。

### F11 阅读统计（需决策 / S–M）

原清单写"不为统计而统计"。折中方案：只做本地、只做"本周阅读时长 + 读完的书"，不做社交、不做排行榜、不做成就。若仍觉得干扰，可不做。

### F12 回收站补两个出口（P2 / S）

`RecycleBin` 只有"逐本恢复/删除"，没有"全部清空"和容量显示。加一行"共 N 本 · 占用 X MB · 全部清空"。

## 6. 不建议做的事（复核后更确定的）

1. **不要引入第三方 UI 框架或阅读引擎**。现在的零依赖是资产：没有供应链风险、包体小、无网络权限，这也是产品叙事的核心。
2. **不要为了"更专业"加仿真翻页/卷曲**。当前 240 ms 平移动画 + 关闭动画即直达，已经足够稳；卷曲在低端机上几乎必然掉帧。
3. **不要继续扩分类层级**。多分类 + 置顶 + 最近阅读已经把书架的管理成本推到临界点，再加"标签组/文件夹嵌套"会让设置面板失控。
4. **不要做云同步/账号**。它需要 INTERNET，会一次性摧毁"无网络权限"这个最强的信任点。
5. **不要用整库重写换取"实时保存"**。E01/E02 的方向是减少写，不是写得更快。

## 9. 验收口径（建议写进下版 VALIDATION）

- 500 本书库，滚动停止、加书签、改名时主线程无 `StrictMode` 磁盘写告警；
- 听书连续 10 分钟，主线程无单帧 > 16 ms 的高亮相关卡顿（可用 `Choreographer` 打点统计）；
- 4 万字单章从目录跳转到第 60 页，等待 < 500 ms（首次）/ < 100 ms（二次、同排版）；
- 1 万章目录快速滚动到底部，无 `GC_FOR_ALLOC` 尖峰；
- 切换编码后，进度与书签能回到原章节（允许 ±1 段误差）；
- `release` 包：R8 开启、自有签名、无 debug 日志、仍无 INTERNET 权限。

---

**一句话总结**：功能已经够用了，下一阶段的胜负手是"把高频路径上的浪费砍掉"——先让 500 本书的书架和 4 万字的章节都不卡，再谈内置宋体和 EPUB。
