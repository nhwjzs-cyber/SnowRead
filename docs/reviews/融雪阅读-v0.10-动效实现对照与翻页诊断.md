## 二、翻页问题一：过渡不平滑（确定是 bug）

### 根因：位图快照的坐标与实时渲染不一致

`PagedReaderView.java:187-197`：

```java
private Bitmap renderBitmap(StaticLayout page){
    ...
    Bitmap bitmap=Bitmap.createBitmap(width,height,Bitmap.Config.ARGB_8888);
    Canvas canvas=new Canvas(bitmap);canvas.drawColor(pageBackground);
    page.draw(canvas);              // ← 直接画，没有 translate padding
    return bitmap;
}
```

对比同一文件里实时渲染的 `drawPage`（`:347-350`）：

```java
private void drawPage(Canvas canvas,StaticLayout page,float x){
    canvas.save();canvas.translate(x,0);canvas.clipRect(0,0,contentWidth(),contentHeight());
    canvas.drawColor(pageBackground);page.draw(canvas);canvas.restore();
}
```

以及 `onDraw` 的入口（`:364-366`）：

```java
canvas.clipRect(getPaddingLeft(),getPaddingTop(),getWidth()-getPaddingRight(),getHeight()-getPaddingBottom());
canvas.translate(getPaddingLeft(),getPaddingTop());
```

### 为什么这会造成"过渡不平滑"

`StaticLayout` 是在 `contentWidth()` 宽度下排版的，文字从 layout 内部的 x=0 开始。但**实时绘制路径**在 `onDraw` 里先 `translate(paddingLeft, paddingTop)`，文字实际出现在屏幕的 `paddingLeft` 处。

而**位图路径**创建的 bitmap 宽高等于 `contentWidth × contentHeight`，文字画在 bitmap 内的 x=0 处；这张 bitmap 在 `onDraw` 里又被 `canvas.drawBitmap(outgoingBitmap, oldX, 0, null)` 绘制 —— 而此时 canvas 已经平移过 padding。

**结果是：动画期间的文字比静止时左移了 `paddingLeft`（通常 20~40dp）。**

用户看到的过程是：翻页动画一开始，**文字整体向左跳一下**，动画结束后又跳回来。这正是"过渡不平滑"。

更糟的是这个跳变**每帧都在**：因为位图和实时布局的偏移量恒定，动画的每一帧都是"错位的字在滑"，所以不是一次性的跳，而是整段动画都在一个错误的位置上滑动 —— 眼睛非常敏感。

### 修复

```java
private Bitmap renderBitmap(StaticLayout page){
    if(page==null)return null;
    int width=contentWidth(),height=contentHeight();
    if(width<=0||height<=0)return null;
    try{
        Bitmap bitmap=Bitmap.createBitmap(width,height,Bitmap.Config.ARGB_8888);
        Canvas canvas=new Canvas(bitmap);
        canvas.drawColor(pageBackground);
        canvas.translate(getPaddingLeft(),getPaddingTop());   // ← 补上这行
        page.draw(canvas);
        return bitmap;
    }catch(OutOfMemoryError error){return null;}
}
```

但这样还不够 —— 见下一节，因为位图的**尺寸**本身也是错的。

## 三、翻页问题二：动画过后一瞬间的拉回（确定是 bug）

### 根因：位图尺寸与绘制坐标系不匹配，动画结束时突变

`renderBitmap` 创建的 bitmap 尺寸是 `contentWidth × contentHeight`（**不含 padding**），但 `onDraw` 里 `canvas.translate(paddingLeft, paddingTop)` 之后才 `drawBitmap(bitmap, oldX, 0)`，绘制原点已经偏了。

而 `onDraw` 的动画分支（`:377-386`）：

```java
}else if(outgoingLayout!=null){
    float oldX=-slideDirection*width*slideFraction,newX=slideDirection*width*(1-slideFraction);
    if(outgoingBitmap!=null&&incomingBitmap!=null){
        canvas.drawBitmap(outgoingBitmap,oldX,0,null);
        canvas.drawBitmap(incomingBitmap,newX,0,null);
    }else{ ... }
```

`oldX`/`newX` 是相对**内容区**（已平移 padding）的坐标，但 bitmap 自身只有内容区大小、没有 padding 偏移 —— 于是：

1. 动画期间：文字出现在 `paddingLeft + 0` 处（错位）；
2. 动画结束（`:181`）：`outgoingLayout=null; slideFraction=1; recycleBitmaps(); invalidate();`
3. 下一帧走 `else drawPage(canvas,layout,0)` 分支 —— **实时渲染**，文字回到 `paddingLeft` 处（正确）。

**所以动画的最后一帧和动画结束后的第一帧，文字横向位置差了一个 `paddingLeft`。** 这就是你说的"翻页动画过后有一瞬间的拉回" —— 不是错觉，是一次实打实的 20~40dp 横向跳变。

### 修复（两处一起改）

正确的做法是让位图包含完整的 view 区域，这样绘制时不需要额外平移：

```java
private Bitmap renderBitmap(StaticLayout page){
    if(page==null)return null;
    int width=getWidth(),height=getHeight();          // ← 用整个 view 尺寸
    if(width<=0||height<=0)return null;
    try{
        Bitmap bitmap=Bitmap.createBitmap(width,height,Bitmap.Config.ARGB_8888);
        Canvas canvas=new Canvas(bitmap);
        canvas.drawColor(pageBackground);
        canvas.translate(getPaddingLeft(),getPaddingTop());
        page.draw(canvas);
        return bitmap;
    }catch(OutOfMemoryError error){return null;}
}
```

同时 `onDraw` 里绘制位图时**不能**沿用已经平移过的 canvas。最干净的做法是动画分支里把 canvas 平移还原：

```java
}else if(outgoingLayout!=null){
    float oldX=-slideDirection*width*slideFraction,newX=slideDirection*width*(1-slideFraction);
    if(outgoingBitmap!=null&&incomingBitmap!=null){
        canvas.save();
        canvas.translate(-getPaddingLeft(),-getPaddingTop());   // ← 抵消外层平移
        canvas.drawBitmap(outgoingBitmap,oldX,0,null);
        canvas.drawBitmap(incomingBitmap,newX,0,null);
        canvas.restore();
    }else{ ... }
```

**注意**：`oldX`/`newX` 的语义也要跟着调整。因为位图现在是整页尺寸（含 padding），位图的左边缘对应屏幕 x=0，所以绘制位图时 x 参数应当是 `oldX - paddingLeft`（`oldX` 仍是内容区坐标系里的页偏移）。最稳妥的写法是统一在内容区坐标系里算，再减掉 padding：

```java
canvas.drawBitmap(outgoingBitmap, oldX-getPaddingLeft(), -getPaddingTop(), null);
canvas.drawBitmap(incomingBitmap, newX-getPaddingLeft(), -getPaddingTop(), null);
```

### 另一种更省事的修法

如果不想动位图坐标系，**直接放弃位图方案**，回到实时渲染：

```java
// 删掉 renderBitmap / recycleBitmaps / outgoingBitmap / incomingBitmap
// onDraw 里恢复为：
drawPage(canvas,outgoingLayout,oldX);drawPage(canvas,layout,newX);
```

代价是每帧重绘两页文本（M5 想解决的性能问题会回来），但**正确性优先**。考虑到 M5 的位图方案本身就有坐标 bug，而且翻页动画只有 240ms、每帧重绘在现代设备上完全扛得住，我倾向先回退到位图修复版，若实测掉帧再考虑第三条路。

## 四、翻页问题三：粘滞感（三重叠加）

### 原因一：系统倍率被乘了两次 ★★☆

`Motion.java:58-62`：

```java
static long scaled(Context context,long duration){
    float factor=scale(context);
    if(factor<=0f)return 0L;
    return Math.max(1L,Math.round(duration*factor));   // ← 已经乘了一次
}
```

而 `Motion.java:82`：

```java
view.animate()....setDuration(actual)   // ← actual 已经含 factor
```

**关键点**：`ValueAnimator.setDuration()` 和 `ViewPropertyAnimator.setDuration()` 设置的是**基础时长**，Android 框架在 `ValueAnimator.getScaledDuration()` 里**会自己再乘一次系统 `ANIMATOR_DURATION_SCALE`**。所以：

> 系统倍率 1× → 240ms（正常）
> 系统倍率 2× → 期望 480ms，实际 **960ms**
> 系统倍率 0.5× → 期望 120ms，实际 **240ms**

这正是 GPT 自己在 `融雪阅读-下一阶段开发与验收清单-v0.10.md` 的 **R03** 里已经写明的问题 —— **它知道这个问题，但没修**。清单原文：

> 标准 Animator 路径会重复缩放；例如基础 240ms、系统倍率 2 时约变成 960ms，而预期约为 480ms。

**这对你的"粘滞感"影响是直接且显著的**：如果你的手机系统动画倍率不是 1×（很多国产 ROM 默认 1.5×~2×，红米/小米系尤其常见），那所有动效都会比设计值慢 1 倍以上，翻页会明显"拖泥带水"。

**修复**：

```java
// Motion.java —— 删掉 scaled() 的乘法，或让标准 Animator 路径不再调用它
static long scaled(Context context,long duration){
    float factor=scale(context);
    if(factor<=0f)return 0L;
    return duration;    // 标准 Animator 自己会乘系统倍率，不要在这里乘
}
```

但要注意区分两类调用：
- **标准 Animator 路径**（`ValueAnimator`、`view.animate()`）：传**基础时长**，系统自动缩放；
- **手工计时路径**（如果将来有基于 `Choreographer` 或 `SystemClock` 的动画）：需要**手动**乘。

`Motion.scaled()` 当前唯一的消费者就是 `PagedReaderView` 的 3 处 `ValueAnimator`（`:176, 243, 313`）—— 全是标准路径，**所以直接让 `scaled()` 返回基础时长即可**。同时 `Motion.to()` 里的 `actual` 也要改成基础时长。

**保留的职责**：`scale()==0` 时禁用动画的判断仍然要保留（这是用户显式关掉动画的意图），不能因为"系统会自己缩放"就丢掉。

### 原因二：邻页异步预排版存在竞态 ★★☆

`PagedReaderView.java:328-346`：

```java
private void requestDragNeighbour(int direction){
    ...
    worker.execute(()->{
        try{
            int end=fitPage(doc.text,targetOffset,limit,measurePaint,width,height,lineSpacing);
            final StaticLayout prepared=typography.layout(...);
            post(()->{if(!disposed&&ticket.get()==token&&dragging)dragNeighbour=prepared;});
        }catch(Exception ignored){}
    });
}
```

问题在于：拖动开始时 `dragNeighbour` 是 **null**，要等 worker 线程排完版才填上。而 `worker` 是**单线程**执行器，正在处理 `navigate()` 的分页任务。

**时序**：
1. 用户开始拖动 → `requestDragNeighbour()` 提交任务到 worker；
2. worker 还在处理上一个分页任务（或这个任务本身要排一页文字）；
3. 用户手指已经移动了 100dp，但 `dragNeighbour` 仍是 null；
4. `onDraw` 走到 `:370` 的 `if(dragNeighbour!=null)` → **不画邻页** → 用户看到的是"页面被拖走，底下是空白纸色"；
5. 几百毫秒后邻页才突然出现 —— **页面内容"啪"地补上**。

**这就是"粘滞感"的直接来源**：手感上像页面被橡皮筋拽着、内容追不上手指。

而且 `worker` 只有一个线程，`requestDragNeighbour` 和 `navigate` 的分页任务**互相排队**，在低端机上会明显串行化。

**修复（三个方向，建议同时做）**：

1. **用独立的 executor 跑预排版**，不要和分页任务抢同一个单线程：
   ```java
   private final ExecutorService neighbourWorker=Executors.newSingleThreadExecutor();
   ```
2. **降级绘制**：邻页没准备好时，先画一块纸色 + 一条淡淡的边界阴影（而不是完全空白），视觉上至少是"一页纸"而不是"空洞"。
3. **提前预取**：翻页动画开始时（`startTransition`）就顺手把下一段排好，而不是等用户开始拖才排。

另外 `requestDragNeighbour` 里 `catch(Exception ignored){}` 静默吞掉异常，排版失败时用户永远看不到邻页，也无从知道发生了什么。

### 原因三：阻尼系数过大 ★☆☆

`PagedReaderView.java:267-268`：

```java
if(next>0)next=next*.35f;
if(next<-width)next=-width+(next+width)*.35f;
```

0.35 意味着**在第一页往右拖 100px，页面只动 35px**。这个手感确实"粘" —— 手指和页面之间有明显的"失配"。

参考值：iOS Books 的回弹阻尼约 0.55~0.7，Android ViewPager 的 EdgeEffect 约 0.5。**0.35 偏激进**。

**建议改为 0.55**：

```java
private static final float RUBBER_BAND=0.55f;
if(next>0)next=next*RUBBER_BAND;
if(next<-width)next=-width+(next+width)*RUBBER_BAND;
```

### 原因四：拖动阈值判定偏严 ★☆☆

`PagedReaderView.java:290`：

```java
boolean commit=travelled>width*.4f||speed>800f*density;
```

`width*.4f` 是 40% 页宽。多数阅读器的阈值在 **25%~30%**。40% 偏大，导致用户"明明拖了半页却被弹回"，这也会被感知为粘滞。

另外 `speed>800f*density` 这里 `density` 是 px/dp 换算系数，`800f*density` 得到的是 px/s，作为速度阈值是合理的，但**这个速度是从 `beginDrag` 里用相邻两帧位移手工算的**（`:270-275`），采样间隔极短（两帧之间可能只有 8ms），容易产生噪声。改用 `VelocityTracker` 更准（`SheetDragLayout` 已经正确用了 `VelocityTracker`，这里可以对齐）。

### 3. `SwipeActionRow.settle()` 绕过了缩放

`SwipeActionRow.java:35`：

```java
front.animate().translationX(show?-width:0).setDuration(Motion.BASE).start();
```

直接用基础时长 → 系统自动缩放一次 → **这条路径是对的**（倍率 1×）。但它与 `Motion.to()` 的行为**不一致**：`Motion.to()` 走的是已缩放的 `actual`。所以同一个 App 里两类动画的时长规则不同，修复倍率平方时要一并统一。

### 4. `PagedReaderView` 仍有未使用的 import

`PagedReaderView.java:4-5` 保留了 `android.provider.Settings` 和 `android.view.accessibility.*`，但 `animationsAllowed()` 已改为委托 `Motion.enabled()`，这两个 import 现在是无用的。**无害，但说明重构没清干净。**

### 5. `edgePaint` 现在是死代码

`PagedReaderView.java:22, 58` 定义并初始化了 `edgePaint`（1px 硬线），但 `onDraw` 已经改用 `drawBoundary()` 的渐变阴影。**`edgePaint` 再也没有被使用** —— 这是"改了一半"的痕迹。`drawBoundary` 里还有个残留问题：

```java
float depth=Math.min(24f*density,Math.abs(direction)*.5f+1f);
```

`direction` 是**符号**（±1），`Math.abs(direction)` 恒等于 1，所以 `depth` 恒为 `min(24dp, 1.5)` = **1.5px**。渐变阴影几乎不可见。**本意应该是根据页面偏移量计算深度**，写错了。

**修复**：

```java
private void drawBoundary(Canvas canvas,float x,int direction,float offset){
    float width=contentWidth(),height=contentHeight();
    float depth=Math.min(24f*density,Math.abs(offset)*.35f+1f);   // ← 用实际偏移量
    if(depth<=0)return;

}
```
