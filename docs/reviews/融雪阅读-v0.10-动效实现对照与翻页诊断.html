二、问题一：过渡不平滑

根因：位图快照的坐标与实时渲染不一致

PagedReaderView.java:187-197 —— 渲染位图时直接画文本，没有 translate padding：

// renderBitmap
Bitmap bitmap=Bitmap.createBitmap(width,height,Bitmap.Config.ARGB_8888);
Canvas canvas=new Canvas(bitmap);canvas.drawColor(pageBackground);
page.draw(canvas);              // ← 直接画，没有 translate padding
// drawPage（实时渲染路径）
canvas.save();canvas.translate(x,0);canvas.clipRect(0,0,contentWidth(),contentHeight());
canvas.drawColor(pageBackground);page.draw(canvas);canvas.restore();
// onDraw 入口
canvas.clipRect(getPaddingLeft(),...);
canvas.translate(getPaddingLeft(),getPaddingTop());   // ← 实时路径会平移

为什么这会造成不平滑　StaticLayout 在 contentWidth() 宽度下排版，文字从 layout 内部 x=0 开始。实时绘制路径在 onDraw 里先 translate(paddingLeft, paddingTop)，文字实际出现在屏幕 paddingLeft 处；而位图路径的位图内文字在 x=0，这张位图又在已平移过的 canvas 上绘制。

结果：动画期间的文字比静止时整体左移了一个 paddingLeft（通常 20~40dp）。动画一开始文字向左跳一下，结束又跳回来 —— 而且偏移量恒定，所以整段动画每一帧都在错位的位置上滑动，眼睛对此极其敏感。

修复

Bitmap bitmap=Bitmap.createBitmap(width,height,Bitmap.Config.ARGB_8888);
Canvas canvas=new Canvas(bitmap);
canvas.drawColor(pageBackground);
canvas.translate(getPaddingLeft(),getPaddingTop());   // ← 补上这行
page.draw(canvas);

但仅补这一行还不够 —— 位图的尺寸本身也是错的，见下一节。

三、问题二：翻页动画后一瞬间的拉回

根因：位图尺寸与绘制坐标系不匹配，动画结束时突变

位图尺寸是 contentWidth × contentHeight（不含 padding），但 onDraw 里 canvas 已平移过 padding。动画分支 :377-386：

}else if(outgoingLayout!=null){
    float oldX=-slideDirection*width*slideFraction,newX=slideDirection*width*(1-slideFraction);
    if(outgoingBitmap!=null&&incomingBitmap!=null){
        canvas.drawBitmap(outgoingBitmap,oldX,0,null);
        canvas.drawBitmap(incomingBitmap,newX,0,null);
    }

完整时序

  1. 动画期间：文字出现在 paddingLeft + 0 处 —— 错位
  2. 动画结束（:181）：outgoingLayout=null; slideFraction=1; recycleBitmaps(); invalidate();
  3. 下一帧走 else drawPage(canvas,layout,0) —— 实时渲染，文字回到 paddingLeft 处 —— 正确

于是动画最后一帧与结束后第一帧，文字横向位置差了一个 paddingLeft。这就是你看到的「拉回」—— 一次实打实的 20~40dp 横向跳变。

修复：位图包含完整 view 区域

// renderBitmap：用整个 view 尺寸
int width=getWidth(),height=getHeight();
Bitmap bitmap=Bitmap.createBitmap(width,height,Bitmap.Config.ARGB_8888);
Canvas canvas=new Canvas(bitmap);
canvas.drawColor(pageBackground);
canvas.translate(getPaddingLeft(),getPaddingTop());
page.draw(canvas);

// onDraw 动画分支：抵消外层平移
canvas.save();
canvas.translate(-getPaddingLeft(),-getPaddingTop());
canvas.drawBitmap(outgoingBitmap,oldX-getPaddingLeft(),-getPaddingTop(),null);
canvas.drawBitmap(incomingBitmap,newX-getPaddingLeft(),-getPaddingTop(),null);
canvas.restore();
更省事的替代方案　若不想动坐标系，直接回退到位图之前（删掉 renderBitmap/recycleBitmaps，onDraw 恢复 drawPage(canvas,outgoingLayout,oldX); drawPage(canvas,layout,newX);）。代价是每帧重绘两页文本 —— 但翻页只有 240ms，现代设备完全扛得住。正确性优先，这是我会选的方案。

四、问题三：粘滞感（四重叠加）

原因一 ★★☆：系统倍率被乘了两次

Motion.java:58-62 的 scaled() 已经乘了一次系统倍率，而 Motion.java:82 把这个结果交给 view.animate().setDuration(actual)。

关键事实　ValueAnimator.setDuration() 和 ViewPropertyAnimator.setDuration() 设置的是基础时长，Android 框架在 ValueAnimator.getScaledDuration() 里自己会再乘一次系统 ANIMATOR_DURATION_SCALE。
系统倍率期望时长实际时长
1×240ms240ms ✓
2×480ms960ms ✗
0.5×120ms240ms ✗

GPT 知道这个问题但没修 —— 它在 融雪阅读-下一阶段开发与验收清单-v0.10.md 的 R03 里已明确写出「标准 Animator 路径会重复缩放…系统倍率 2 时约变成 960ms，而预期约为 480ms」，但 v0.10 产物里未做修复。这说明它的清单生成与执行是分离的。

修复

// Motion.java —— 标准 Animator 路径传基础时长，系统自己缩放
static long scaled(Context context,long duration){
    float factor=scale(context);
    if(factor<=0f)return 0L;
    return duration;   // 不要在这里乘
}

Motion.scaled() 当前唯一消费者是 PagedReaderView 的 3 处 ValueAnimator（:176, :243, :313）—— 全是标准路径，直接返回基础时长即可。但 scale()==0 时禁用动画的判断要保留，那是用户显式关掉动画的意图。

原因二 ★★☆：邻页异步预排版存在竞态

PagedReaderView.java:328-346 —— 拖动开始时 dragNeighbour 是 null，要等 worker 线程排完版才填上。而 worker 是单线程执行器，正在处理 navigate() 的分页任务。

  1. 用户开始拖动 → requestDragNeighbour() 提交任务
  2. worker 还在处理上一个分页任务
  3. 用户手指已移动 100dp，但 dragNeighbour 仍是 null
  4. onDraw:370 的 if(dragNeighbour!=null) 不成立 → 不画邻页，用户看到「页面被拖走，底下是空白纸色」
  5. 几百毫秒后邻页突然出现 —— 内容「啪」地补上

这就是粘滞感的直接来源：手感像页面被橡皮筋拽着、内容追不上手指。且 catch(Exception ignored){} 静默吞异常，排版失败时用户永远看不到邻页，也无从知道发生了什么。

修复（三选，建议同时做）

  • 独立线程：给邻页预排版单独开一个 executor，不与分页任务抢同一个单线程
  • 降级绘制：邻页未就绪时先画纸色 + 一条淡边界阴影，至少是「一页纸」而非空洞
  • 提前预取：翻页动画开始时（startTransition）顺手排好下一段，而不是等用户开始拖才排

原因三 ★☆☆：阻尼系数过大

PagedReaderView.java:267-268 的 0.35f 意味着在第一页往右拖 100px，页面只动 35px —— 手指与页面之间明显失配。

参考值：iOS Books 回弹阻尼约 0.55~0.7，Android ViewPager EdgeEffect 约 0.5。0.35 偏激进，建议改 0.55f。

原因四 ★☆☆：拖动阈值偏严

PagedReaderView.java:290 的 travelled>width*.4f 是 40% 页宽，多数阅读器在 25%~30%。阈值过大导致「明明拖了半页却被弹回」，也会被感知为粘滞。

另外速度阈值 800f*density 的速度值来自 :270-275 的相邻两帧手工计算（间隔可能只有 8ms），容易产生噪声 —— 建议改用 VelocityTracker（SheetDragLayout 已正确使用，此处可对齐）。
