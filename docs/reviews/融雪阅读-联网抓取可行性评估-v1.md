# 融雪阅读 · 联网抓取（书源）可行性评估

> 评估对象：v0.9.2 源码（36 个文件 / 3,253 行 Java）
> 问题：粘贴网站链接 → 抓取书籍 → 自动分类（如畅销榜）→ 获取书评区，是否可行，复杂到什么程度

---

## 一、结论速览

| 能力 | 可行性 | 复杂度 | 建议 |
|---|---|---|---|
| 粘贴单本书链接 → 入库可读 | **高** | 低，约 2–3 人日 | 值得做 |
| 榜单/分类页 → 批量入库并自动打分类 | **中高** | 中，约 4–6 人日 | 可以做，但必须配规则层 |
| 追更（已有书增量追加章节） | **中** | 高，约 5–7 人日 | 第二阶段，需先改身份模型 |
| 书评区只读展示 | **中** | 中高，约 3–5 人日 | 缓做，收益存疑 |
| 书评区互动（发评、点赞、回复） | **低** | 极高 | 不建议 |
| 任意链接通用抓取（无规则） | **低** | 无上限 | 不建议 |

一句话：**"抓进来能读"很便宜，"一直抓得对"很贵。**

---

## 二、为什么"抓书"比预想便宜——接缝已经存在

现有代码里已经有一条完整的"外部字节 → 可读书籍"通路：

```java
// BatchImporter.run() 正在做的事
byte[] bytes = TextDocument.readLimited(source.open());
LibraryStore.Book book = store.add(bytes, name, encoding, category);
```

`LibraryStore.add(byte[], title, forced, category)` 内部会：
1. 算 SHA-256 得到书籍 ID；
2. `TextDocument.decode()` 自动检测编码；
3. 落盘正文 + 写入 index.json；
4. 传入的 `category` 直接进入 `ShelfOrganization` 的分类。

**也就是说，只要抓取器输出"一个 byte[]、一个标题、一个分类名"，下游全部自动打通。** 不需要章节表——`TextDocument` 的章节是从整串文本用正则推导的（`NUMBERED` / `ENGLISH` / `HEADING`），所以把章节按顺序拼成一大段文本，分章会自动出现。

可直接复用的现成件：

| 现有组件 | 抓取场景下的作用 |
|---|---|
| `TextDocument.decode()` | 网页多为 UTF-8，个别老站 GBK，直接复用 |
| `TitleCleaner` | 清理"《书名》最新章节"这类网页标题 |
| `TaskProgress` / `TaskControl` | 抓取是可取消长任务，进度条与取消语义现成 |
| `BatchImporter` | 批量抓 + 失败回滚 + 去重，语义完全对得上 |
| `ReadingAnchor` / `PositionMigration` | 内容更新后能把进度和书签搬到新文本上 |
| `ShelfOrganization` | 自动分类只需要传 category 字符串 |

**所以"粘贴链接抓一本书"这一层，代码量很小，一天能出原型。**

## 三、为什么"书评"贵得多——数据模型里没有它的位置

`LibraryStore.Book` 的字段是：`id / title / encoding / offset / length / marks / markNotes / typeset / anchor / markAnchors / sourceName`。

**只有"一整本书 = 一串连续文本 + 一个阅读位置"这一种形态。** 书评不是连续文本，它是"带作者、时间、点赞数、回复的列表"，且与正文进度无关。硬塞进去会破坏三个东西：

1. **`index.json` 的 v3 严格校验**——`BookExtras.read()` 对未知字段虽宽容，但对已知字段类型极严，加数组要动 schema；
2. **`BackupArchive` 的路径白名单**——只接受 `library/[a-f0-9]{64}.txt` 和 `library/covers/...jpg`，书评若单独存文件，备份格式要升到 v3 并同时兼容 v1/v2 读取；
3. **备份 manifest 校验**——`bookCount` 与实际条目数必须一致，新增实体要参与计数。

改动面对比：

- 抓一本书：**新增 4 个模块，改动现有代码 0 处**
- 加书评：**新增 5 个模块，改动 6 处现有代码**（Book 模型、index 版本、BookExtras、BackupArchive 白名单、书库 UI、阅读界面）

而且书评区通常要登录才看得到完整内容，公开可见的只有几条短评——**投入产出比明显低于抓书**。

建议：如果真要做，走**旁挂**而不是并入。存 `library/reviews/<bookid>.json`，不进 `index.json`（也顺带避开主线程 fsync 放大），UI 用现成的 `AppSheet` 弹层。

## 四、五个真正会咬人的工程问题

### 1. 书籍 ID 是内容哈希，内容一变就是"另一本书"

`add()` 里 `id = SHA-256(整个文件字节)`。这在本地导入是优点（天然去重），在联网抓取是灾难：

- 站点补了一章 → 哈希变 → **新增一本书，原书进度、书签、笔记全部留在旧书上**；
- 站点改了个广告位/错别字 → 同样结果。

必须引入**稳定身份**：`sourceKey = 站点标识 + 站点内书籍 id`，作为去重与更新依据，content hash 降级为"内容版本号"。

好消息：`ReadingAnchor` 已经按"章节标题 + 段落上下文 + 章内比例 + 全书比例"四重定位，`PositionMigration` 也已经实现了"旧文本→新文本"的批量搬迁（含书签与备注）。**这套东西本来就是为"文本变了但书还是这本"设计的**，抓取更新正好复用，这是这个项目已有的最大资产。

### 2. 12MB 的硬上限会直接挡住大部头

`TextDocument.MAX_BYTES = 12 * 1024 * 1024`。一本 3000 章 × 3000 字的网文，UTF-8 中文约 18MB，**导入时会被拒绝**。

同时 `PagedReaderView.fitPage` 每算一页都会排版 8192 字（此前清单已列为性能问题），书越长、页码索引重建越慢。抓取会把"书很长"从例外变成常态，这两个问题会被放大。

### 3. 章节正则对网页小说的覆盖并不完整

`NUMBERED = ^第[\s]*([零〇一二三四五六七八九十百千万亿两兩壹贰...0-9０-９]+)[\s]*([章节節卷回部篇集])`

能认：`第一章`、`第一千二百三十四章`、`第 12 章`、`第１２章`
认不了：`正文 第12章 xxx`（前缀）、`12. 章节名`（纯数字编号）、`Capitolo 12`、以及部分站点把章节名放在 `<h1>` 但正文首行重复标题导致**每章标题出现两次**。

需要在拼接阶段做归一化：统一成 `第N章 标题` 的单行形式，并且**剥掉正文里重复的标题行**。

### 4. 反爬是"能不能做"的分水岭

按难度递增：

| 障碍 | 应对 | 代价 |
|---|---|---|
| UA / Referer 校验 | 设请求头 | 几乎为零 |
| 频率限制 | 串行 + 延时 | 抓一本 3000 章要几十分钟 |
| 正文在 JS 里渲染 | 只能用 WebView 跑脚本 | 重，需处理生命周期 |
| 字体加密（起点、番茄等） | 需还原字符映射表 | 极重，且随时失效 |
| Cloudflare / 验证码 | 基本无解 | — |

**字体加密这一条基本决定了：主流商业站抓不了，或抓下来是乱码。**

### 5. 这个 App 目前是"零联网"姿态，加网络是产品级变更

现状：**AndroidManifest 里没有 INTERNET 权限**，无第三方依赖，`allowBackup=false`。

加网络意味着同时要补：连接超时/重试策略、并发与限速、离线缓存与失效、隐私政策申报（应用商店必查）、以及"用户数据不出设备"这一条卖点的放弃。这不是代码量问题，是定位问题。

## 五、合规风险（这条会决定功能能否上线）

抓取商业站点的付费/授权内容是明确的著作权风险，批量抓取榜单还可能触及不正当竞争；国内应用商店与 Google Play 对"聚合盗版内容"的下架处理很坚决。

可行的合规路径只有三条：

1. **公版书源**——古籍、古典名著、已进入公有领域的作品，法律上干净，但"畅销榜"就不存在了；
2. **有授权的接口**——出版社/平台提供的开放 API；
3. **用户自建源**——应用只提供"规则引擎 + 抓取能力"，不内置任何站点，规则由用户自己导入（类似 Legado 的做法）。这能显著降低应用本身的责任，但也把可用性门槛转嫁给了用户。

**不建议**内置具体商业站点规则后发布。

## 六、若要做，推荐的最小架构

```
SourceAdapter（接口）
  ├─ list(url, page)      → 榜单/分类条目
  ├─ detail(url)          → 书名、作者、简介、封面、章节目录
  └─ content(url)         → 单章正文纯文本

规则用 JSON 描述，不写死在代码里：
{ "id": "demo", "name": "...", "charset": "utf-8",
  "list":    { "item": "...", "title": "...", "url": "..." },
  "detail":  { "title": "...", "author": "...", "toc": "..." },
  "content": { "body": "...", "remove": ["script", ".ad"] } }
```

要点：
- 网络层用 `HttpURLConnection`，**维持零第三方依赖**（不引 OkHttp/jsoup，HTML 解析写一个极简的标签扫描器即可，现有代码风格本来就是手写）；
- 抓取结果直接交给 `BatchImporter`，进度条、取消、回滚、去重全部白拿；
- 章节正文**按章缓存**到 `cache/source/<bookKey>/<n>.txt`，读完即弃，避免一次性占满内存；
- 入口 UI 极简：书库页一个"从链接添加"，`ClipboardManager` 取剪贴板 + 一个输入框，不需要额外权限。

## 七、分期建议

| 版本 | 内容 | 估时 | 风险 |
|---|---|---|---|
| v1.0 | 单源、单本书、粘贴链接 → 抓完入库 | 2–3 人日 | 低 |
| v1.1 | 榜单页 → 批量入库 + 自动分类 | 4–6 人日 | 中，取决于站点结构稳定性 |
| v1.2 | 追更（需先做 sourceKey 身份改造 + 锚点迁移） | 5–7 人日 | 高，涉及数据迁移 |
| v1.3 | 书评只读（旁挂 storage + AppSheet 展示） | 3–5 人日 | 中 |
| — | 通用抓取 / 书评互动 | 不建议 | — |

**如果只做一步**：做 v1.0，先验证"抓下来的文本干净到可以直接听书"。因为分章错、广告没洗干净，听书会念出"本章未完请点击下一页"，体验立刻崩——**文本清洗质量比抓取数量重要一个数量级**。

## 八、和现有待办清单的关系

- 此前的"分页性能"（`fitPage` 每次排版 8192 字）与"写库移出主线程"，在引入抓取后**从"优化项"升级为"前置依赖"**——长书 + 频繁入库会把这两个问题同时引爆；
- `ReadingAnchor` / `PositionMigration` 原本是为"切换编码不丢进度"做的，现在成了"追更不丢进度"的基础设施，优先级应上调；
- 建议顺序：**先修分页与写库 → 再做抓取 → 最后考虑追更与书评**。
