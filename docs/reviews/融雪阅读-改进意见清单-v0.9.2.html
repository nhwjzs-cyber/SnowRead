01摘要：如果只看一页

工程质量整体偏上——纯 Java 文本引擎与 Android 解耦、索引原子写、备份逐字节校验、长任务可取消、零依赖、无网络权限。这些不要动。真正的瓶颈已经不在功能数量，而在三条高频路径。

  1. 体验瓶颈集中在写库、听书高亮、分页测量三条路径，而不是缺少功能。
  2. 写库在主线程 fsync：滚动停止、加书签、改名都会卡一下；500 本时每次序列化百 KB 级 JSON。
  3. 听书每朗读一个词就重建整页 StaticLayout，并把整个列表 notifyDataSetChanged()。
  4. 分页每算一页都排版 8192 字，而一页通常只有 300–600 字；页索引不落盘，改字号全部重算。
  5. 四个列表没有复用 convertView，目录上万项时滚动成本随距离线性增长。
  6. 5 个 P0 合计约 5–7 人日，能清掉大部分"卡一下"的体感问题，且不改数据结构与格式版本。
  7. 功能上最值得补的三个洞：内置开源宋体、按书独立排版、阅读位置与编码解耦。
  8. 最该克制的：继续增加管理维度。书架的管理成本已接近临界点。

02效率与性能 · P0

五项都能被用户直接感知，且都不需要改数据格式。建议下一版集中处理。

E01书库在主线程写盘并 fsync M

证据
MainActivity.persist():585 直接调用 LibraryStore.save():140-146，后者 metadata() 序列化全部书籍，再经 AtomicFile.finishWrite() 落盘（内含 fsync）。调用点全在 UI 线程：滚动停止 :466、翻页 :453、退出 :586、开书 :423、排版预览 :668，以及加书签 :800、改名 :866、分类 :223。
问题
500 本时每次保存要构建 500 个 JSONObject + 序列化 + 写盘 + fsync，量级百 KB / 5–20 ms。它恰好发生在"手指刚停下"的瞬间，是最容易被感知为卡顿的位置；听书时还会与 IO 线程争锁。
建议
引入单一写库通道 LibraryWriter：内存模型立即改，落盘走单线程 + dirty 标记 + 200–400 ms 合并窗口；onPause、退出阅读、导入结束、备份前强制 flush；写失败回滚快照并提示。LibraryStore.save() 保持同步语义，只是不再由 UI 线程调用。
收益
消除滚动停止、加书签、改名时的主线程 fsync，写盘次数从"每次动作"降到"每次窗口"。

E02听书每朗读一句就整库重写 S

证据
ListenService.save(boolean):139 → LibraryRepository.progress():33-38 → store.save()。onStart 回调（:69）每句都调用 save(false)；force=false 只做"同时只有一个在飞"的合并，不做时间窗合并，因此约每句（3–6 秒）落盘一次全量索引。
问题
听书 1 小时 ≈ 600–1000 次全量写 + fsync。耗电、闪存写放大，并在朗读间隙可能触发 GC 与 IO 抖动。
建议
进度按"每 10 秒 或 章节切换"落盘；pause / stop / onDestroy / 切书强制落盘；句子粒度只更新内存 Book.offset。复用 E01 的同一通道，避免两套写路径。
收益
写盘频率降一个数量级；长播耗电与抖动明显下降。

E03词级高亮触发整页重排与整个列表重绑 M

链路
TtsEngine.onRangeStart:43 → ListenService.range():70 → publish(false) → MainActivity.onListeningChanged:881 → refreshHighlights():580：分页模式走 PagedReaderView.render():167 重建 Spannable + StaticLayout；滚动模式走 readerAdapter.notifyDataSetChanged()。而 onRangeStart 是按词触发的，中文 TTS 约每秒 4–6 次。
问题
朗读时每秒 4–6 次整页文字 shaping + 整表重绑，中低端机会直接掉帧。这是"听书时页面发飘"的根因。

E04每算一页都排版 8192 字 M

证据
PagedReaderView.fitPage():120-132：windowEnd = start + 8192，每次新建 StaticLayout，只取"第一屏放得下的行"，然后整份 layout 丢弃；下一页再从 start 重排。
问题
一页 300–600 字，却为它 shaping 8192 字，约 10–20 倍浪费。长章节（4 万字 ≈ 70 页）首次进入或深层跳转时，用户在"正在定位页面…"上的等待基本由这里决定。
建议
滑动窗口批量切页：一次 layout 覆盖 8–16 K 字后，用同一个 StaticLayout 连续切出多页（getLineStart/getLineTop 直到高度用尽），窗口耗尽再推进；把 PageIndex.extend() 的 Fitter 从"切一页"扩展为"切一批"。保留代理对边界处理。
收益
分页吞吐提升约一个数量级；长章节首次进入从秒级降到百毫秒级。

E05四个列表都没有复用 convertView M

证据
ShelfAdapter:206 每次新建 LinearLayout 子类 + BookCoverView + ShelfTitleView + 徽标 + 进度条，完全忽略 reused；chapters():592、search():646、AppSheet:71 同样每次新建。只有 ReaderAdapter:898 正确复用了 TextView。
问题
目录最多 1 万项、搜索 1000 条、书架数百本，滚动时每帧都在建 View 树并触发 measure/layout；书架还叠加自定义封面绘制，单帧成本最高。
建议
标准 ViewHolder 复用。书架复用时必须额外处理三件事：清空旧 bitmap（避免串封面）、Motion.reset(tile) 复位按压态、重算选中/置顶徽标。ShelfTitleView 的自适应字号结果按 (title, width) 缓存，避免每次 measure 试 5 个字号。
收益
目录与书架帧率提升最明显，内存分配下降、GC 抖动减少。

05功能改进建议

此处只列原待办清单之外的新提案；清单已列的（导入预览、TXT 清洗、列表视图、排序、阅读状态、大文件、虚拟分章、自动备份、崩溃日志等）见第 08 节。

F01 内置一款开源宋体 M

设置里现在写"宋体字形由手机字体支持情况决定"，而国产 ROM 上 SERIF 常回落到黑体。内置思源宋体/霞鹜文楷子集（7000 常用字 ≈ 3–6 MB），或"内置宋体 / 系统字体"二选一。这是阅读器最核心的"字"，也是与同类拉开差距最直接的一处。

F02 按书独立记忆排版 S–M

字号、行距、页边距、主题、常亮目前全局共享。给 Book 加可选 typeset 覆盖字段（缺省跟随全局），在"Aa 排版"顶部加"仅对本书生效"。可选字段不破坏 v3 格式与旧备份。

F03 阅读位置与编码解耦 M

现在 offset 是全文偏移，切编码直接归零并清空书签。改为"章序号 + 章内偏移/比例"，切换时按章节标题+比例重定位，映射失败的书签单独列出而不是整体清空。顺带解决"文本被替换后进度错位"。

F04 进度条上标书签 S

在 SeekBar 上方叠 2 dp 刻度条，把 active.marks 画成小点，点按直达；长按进度条进"章号跳转"。成本极低，但"这本书我标过哪"变得一眼可见。

F05 阅读手势可配置 S–M

双指上下滑调亮度（阅读器通用手势，不用退出阅读）；双击中间收藏书签；上/下滑翻页（可关）；音量键长按连续翻页（现在只处理 repeatCount==0）。

F06 听书：预合成下一句 M

每句都 QUEUE_FLUSH 等引擎起播，句间有 300–800 ms 空白。当前句播放时用 synthesizeToFile 预生成下一句，onDone 后直接播文件，不支持则静默回退。另加"长按选段 → 从这段开始朗读"。

F07 导入清洗书名 + 编码打分 M

书名现在原样取文件名（[完结]《xxx》(1-1000章)作者：yyy）；编码只在 UTF-8 失败时盲选 GB18030，Big5 会静默乱码。加书名清洗规则 + "常用字命中率"打分，并在预览里显示置信度。

F08 书架规模化 M

右侧 A–Z / 拼音首字母索引条；长按拖动自定义排序（新增 order 字段，缺省回落最近打开）；多选支持批量导出/批量移出（现在批量只有置顶与分类）。

F09 搜索增强 S–M

英文忽略大小写（regionMatches(true,…) 保 offset 映射）；结果按章节分组折叠；"仅本章内查找"；最近 10 条搜索历史。跨书搜索仍建议等索引方案。

F10 EPUB 支持 L

唯一能显著扩大受众、也唯一会动摇"纯 TXT + 极简"定位的功能。最小路径：ZIP → container.xml/.opf/spine → XHTML 转纯文本段落后复用现有分章分页。建议先做产品决策，不排期。

F11 阅读统计（需决策） S–M

原清单写"不为统计而统计"。折中：只做本地"本周阅读时长 + 读完的书"，不做社交、排行榜、成就。若仍觉得干扰可不做。

F12 回收站补两个出口 S

现在只能逐本恢复/删除。加一行"共 N 本 · 占用 X MB · 全部清空"。

07不建议做的事

不要引入第三方 UI 框架或阅读引擎。零依赖是资产：无供应链风险、包体小、无网络权限，也是产品叙事核心。
不要做仿真翻页 / 卷曲。当前 240 ms 平移 + 关闭动画即直达已经够稳；卷曲在低端机上几乎必然掉帧。
不要继续扩分类层级。多分类 + 置顶 + 最近阅读已把管理成本推到临界点，再加标签组/文件夹嵌套会让设置面板失控。
不要做云同步 / 账号。它需要 INTERNET，会一次性摧毁"无网络权限"这个最强的信任点。

如果只能先做三件：
① E01 + E02 把写库移出主线程并合并——改一个类，覆盖所有"卡一下"的体感；
② E03 + E04 高亮与排版解耦、分页批量测量——听书与长章节两个主场景；
③ E05 + E07 列表复用 + 封面绘制缓存——书架、目录、搜索三个列表。
第 4、5 件：B01/B03（导入与听书的行为 bug）、F01（内置宋体）。

验收口径（建议写进下版 VALIDATION）

· 500 本书库，滚动停止 / 加书签 / 改名时主线程无 StrictMode 磁盘写告警
· 听书连续 10 分钟，无高亮相关的单帧 > 16 ms（Choreographer 打点统计）
· 4 万字单章从目录跳到第 60 页：首次 < 500 ms，二次（同排版）< 100 ms
· 1 万章目录快速滚到底部，无 GC_FOR_ALLOC 尖峰
· 切换编码后进度与书签能回到原章节（允许 ±1 段误差）
· release 包：R8 开启、自有签名、无 debug 日志、仍无 INTERNET 权限

一句话总结：功能已经够用了，下一阶段的胜负手是"把高频路径上的浪费砍掉"——先让 500 本书的书架和 4 万字的章节都不卡，再谈内置宋体和 EPUB。
