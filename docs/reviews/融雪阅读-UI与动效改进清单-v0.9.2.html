第一梯队动效结构问题

M1★★翻页不跟手，而且慢速拖动完全无效

证据

new GestureDetector.SimpleOnGestureListener(){
    @Override public boolean onSingleTapUp(MotionEvent e){ ... }   // 点按：翻页
    @Override public boolean onFling(MotionEvent f,MotionEvent l,float vx,float vy){
        if(Math.abs(dx)>48*density && Math.abs(dx)>Math.abs(dy)){ ... next(); }
    }
    // 没有 onScroll，没有位移跟踪
}

PagedReaderView.java:51-67 · 翻页动画在 :133-138 分页完成后才播

问题

  • 翻页只有两条路径——点按左右 1/3，或甩动（onFling）。中间没有任何"手指带着页面走"的实现。
  • 更糟：onFling 要求 |dx| > 48dp，但 onScroll 未实现、位移也不跟踪。用户慢慢拖动超过 48dp（没甩、速度不够）→ 什么都不会发生，页面纹丝不动，用户会以为 App 卡了，然后改用点按。
  • 现有 240ms 整页横移动画与用户手势之间没有任何因果关系——用户无法控制翻页的力度、位置、速度。

为什么重要

翻页是阅读器唯一的高频交互，当前实现把它变成了"二选一"的离散操作。市面上所有成熟阅读器（Kindle / 多看 / 掌阅 / iBooks）都提供跟手拖动，这是差距最大的一处交互。

建议

  1. 实现 onScroll：累积横向位移，用 translationX 让当前页跟随手指实时平移（drawPage(canvas, layout, x) 的绘制能力已具备，只需把 x 从动画器换成手势值）；
  2. 松手时按位移阈值 + 速度双条件决定是否翻页（位移 > 40% 页宽 或 速度 > 800dp/s），否则用 Motion 的减速曲线弹回；
  3. 点按 / 按键翻页保留现有 240ms 动画不动，两条路径互不干扰；
  4. 边界（已是第一页 / 已到书末）加入轻微阻尼位移 + 一次轻触感，而不是现在弹一个 Toast（见 M10）。

M2★★长任务的进度文字在闪烁

证据

// Motion.java:47

    boolean animating=running.containsKey(view);
    view.setText(value);
    if(!animating) enter(view,0,FAST);      // ← 整段文字 alpha 0 → 1
}

// TaskProgress.render()，每 120ms 调一次

Motion.java:47 · TaskProgress.java:46 · Motion.FAST=120ms

问题

Motion.text 每次都把整个标签重置到 alpha=0 再淡入到 1，而刷新节奏同样是 120ms。alpha 呈锯齿状反复从 0 爬到 1。导入 500 个文件时，进度那行字一直在"半透明↔不透明"之间抖，看起来像一个坏掉的显示屏，而不是一个在正常工作的进度指示。

为什么重要

  • 这直接违反自己写的验收标准——动效规范 §9 明确写着"批量导入 500 个文件时，进度条持续前进，文字切换不闪"。
  • 长任务里闪烁会被误读为"出错了 / 卡住了"，反而制造焦虑。规范 §1 的总原则是"进度表达：让用户看到在动"——现在看到的是"在抽搐"。

建议

  1. Motion.text 改为不重置 alpha：只在文字首次出现时做一次淡入，之后纯 setText；
  2. 若要让"数字在变"被感知，把变化做在颜色上：百分比用 accent 色、描述用 muted 色，120ms 交叉过渡，而不是整段 alpha 归零；
  3. 保留淡入的场景只有一个：文件名从"正在整理书页…"变成具体文件名时做一次 120ms 交叉淡入——这才是规范 §4"文件名 120ms 交叉淡入"的原意。

M3★★系统级动画缩放被完全忽略（无障碍缺陷，不是口味问题）

证据

try{return Settings.Global.getFloat(context.getContentResolver(),
        Settings.Global.ANIMATOR_DURATION_SCALE,1)>0
     && Settings.Global.getFloat(context.getContentResolver(),
        Settings.Global.TRANSITION_ANIMATION_SCALE,1)>0;}
catch(Exception ignored){return true;}

Motion.java:27

问题

代码只判断"缩放是否 > 0"（决定动画开不开），却从不把缩放值乘进时长。用户在系统辅助功能里把"动画时长"调到 0.5× 或 2×，这个应用的所有动效时长纹丝不动，永远是写死的 120 / 180 / 220 / 240ms。

为什么重要

  • 慢速动画（0.5×）是前庭功能敏感用户、演示模式、以及需要看清细节的用户明确表达的需求。忽略它等于剥夺了系统提供的无障碍设置——这是无障碍缺陷，不是设计分歧。
  • 并且 ANIMATOR_DURATION_SCALE 与 TRANSITION_ANIMATION_SCALE 混在一个布尔判断里，语义混乱。
  • PagedReaderView.animationsAllowed()（:139-146）还自己实现了一份重复逻辑，两处必然漂移。

建议

  1. Motion 增加 static float scale(Context)，读取并缓存缩放值（见 M4）；
  2. 所有时长统一走 duration(base) = round(base * scale)，scale == 0 时走现有的"直接落到终态"路径；
  3. 设定上限（如 3×），避免用户把系统调到 10× 时界面变得无法使用；
  4. 把"减少动效"开关与系统缩放的关系写进设置项说明，避免困惑；PagedReaderView.animationsAllowed() 改为直接调用 Motion.enabled()。

M4★★每次动画启动都做一次跨进程查询

证据

// Motion.enabled() —— 每一个原语入口都会走到
AccessibilityManager manager=(AccessibilityManager)context.getSystemService(ACCESSIBILITY_SERVICE);
Settings.Global.getFloat(context.getContentResolver(), ANIMATOR_DURATION_SCALE, 1)

Motion.java:27 · PagedReaderView.java:141-145

问题

Settings.Global.getFloat 不是读本地内存，它要通过 ContentResolver 向系统设置服务发一次 binder 调用。而 Motion.enabled() 在 to() 内部、enter/exit/press/release/confirm/badge/text 的每个入口都会走一遍；翻页时还会再调一次自己那份实现。

也就是说：每次翻页、每次面板开合、每次按钮按压的开头，都夹着一次跨进程 IPC。在低端机上这足以贡献一帧的可感知延迟——而且它恰好发生在"动画开始"这个最需要准时的时间点上，直接体现为动画起步的顿挫感。

建议

  1. Motion 里加静态缓存 static volatile float cachedScale = 1f;；
  2. 刷新时机：onResume()、已有的 nightTick（30s 定时器）、prefs 变化时；
  3. AccessibilityManager 同样缓存为静态字段（已有清单 E08 提过 dispatchTouchEvent 里的重复查询，动画路径上的这处是独立的一处，那份清单没覆盖）；
  4. PagedReaderView.animationsAllowed() 删掉重复实现。

M5★★翻页动画每帧重绘两个整页文本，而且从未启用硬件层

证据

private void drawPage(Canvas canvas,StaticLayout page,float x){
    canvas.save();canvas.translate(x,0);canvas.clipRect(0,0,contentWidth(),contentHeight());
    canvas.drawColor(pageBackground);        // ← 全屏色块填充
    page.draw(canvas);                        // ← 整页文本重绘
    canvas.restore();
}
// onDraw：翻页期间每帧调用两次

PagedReaderView.java:193-207 · grep LAYER_TYPE 结果只有 LAYER_TYPE_NONE

问题

  • 240ms 内约 14 帧，每帧做 2 次全屏 drawColor + 2 次整页 StaticLayout.draw（1080p 上是两块 ~1080×1900 区域）。
  • 更关键：动效规范 §8.5 明确写着"动画期间可给 panel 加 LAYER_TYPE_HARDWARE，结束后恢复 LAYER_TYPE_NONE"，代码里一次都没有实现。Motion.cancel() 里那句 setLayerType(NONE) 是在收尾，但从头到尾没有谁把它设成 HARDWARE。

为什么重要

掉帧会直接毁掉翻页动效本身——这是全 App 唯一一个每帧都发生的大面积重绘。翻页"发飘"、"不跟手"（M1）的观感，有一部分其实是掉帧而不是设计问题。这与已有清单 E03（听书整页重排）属于同一类体感，但成因不同、位置不同，那份清单没覆盖到这里。

建议

  1. Motion.to() 启动动画时对目标 View 设 LAYER_TYPE_HARDWARE（cancel() 已会恢复 NONE，只需补上开始这一侧）；
  2. 翻页动画期间把两个 StaticLayout 各渲染一次到离屏缓存（或把整个 PagedReaderView 提升为硬件层），让每帧只做位图平移；
  3. drawColor 换成只填充"即将露出的那一侧"，避免整屏填两遍；
  4. 边界那条 1px 硬线（edgePaint，alpha=24）建议改成带方向的渐变阴影（LinearGradient 从透明到 12% 黑），同样成本，观感提升明显。

问题

  • 开关的滑块位置瞬移，轨道颜色瞬变（invalidate() 重绘，没有插值）；
  • ChoiceStrip.update() 切换时直接 setBackground(新drawable) + setTextColor，背景与文字色瞬间跳变；

建议

  1. ToggleRow：把 checked 从 boolean 改成 float 0→1 的动画值，用 ValueAnimator（180ms，decelerate）插值滑块位置与轨道色——自绘控件改造成本极低；
  2. ChoiceStrip：选中态背景与文字色用交叉淡入；
  3. ThemeSwatches：环的粗细用 Paint stroke 宽度做 180ms 插值，"Aa"↔"✓" 切换用 120ms 淡出淡入；
  4. 这三条都可以在 Motion 里加两个新原语供所有自绘控件复用。

M8★面板回弹没有物理感；规范里的第三种缓动从未存在

证据

// Motion.java —— 规范 §2 列了三种曲线，实际只有两种
private static final DecelerateInterpolator IN=new DecelerateInterpolator(1.4f);
private static final AccelerateInterpolator OUT=new AccelerateInterpolator(1.2f);
// 规范 §2 的 EASE_STD（FastOutSlowInInterpolator）没有定义、没有使用

// SheetDragLayout —— 松手回弹
if(close)close(); else Motion.settleSheet(this,window);   // → to(panel,1,0,1,BASE,true,null)，纯减速

Motion.java:17-18 · SheetDragLayout.java:34,38

问题

拖动面板松手后的回位，是全 App 手感最强的一个瞬间。现在用一条纯减速曲线收尾，面板像被"吸"回原位，而不是被"放"回原位。缺一点点过冲，物理感就少一半。拖拽跟手是 1:1 硬跟随，没有阻尼；松手与拖动之间是两种截然不同的手感。

为什么重要

规范 §1 写"安静：不弹跳、不旋转、不闪烁"，这条原则本身是对的——但"安静"指的是不要装饰性弹跳，不是"不许有过冲"。0.5% 量级的过冲属于物理反馈，不是装饰。业界标准（Material 3、Flutter 的 Curves.easeOutBack）都在手势回弹上使用极小的过冲。

建议

  1. Motion 补齐规范 §2 承诺的第三种曲线 EASE_STD = FastOutSlowInInterpolator，用于交叉淡入与面板回弹；
  2. 新增 EASE_BACK = OvershootInterpolator(1.06f)（过冲量必须小），仅用于 SheetDragLayout.settleSheet() 与 SwipeActionRow.settle() 两个手势回弹场景；
  3. 拖拽过程中给 translationY 加 0.85 阻尼系数，让面板"沉"一点而不是死板地跟着走；
  4. 在动效规范 §2 的表格里把每种曲线的适用场景写清楚，避免下一个版本又出现"规范有、实现没有"的漂移——这是本文档反复出现的一个模式。

  • chapterLabel 占内容区 y = 24–56（状态栏内边距 24dp）；顶栏占 y = 32–92 → 重叠 24dp，章节名被压住；

为什么重要

阅读时用户最想看的两件事——"我在第几章"和"读到百分之几"——恰恰在工具栏显示时被挡住。而工具栏默认显示 4 秒（ReaderChrome.IDLE_MS=4000）才自动收起。用户进书后的前 4 秒，看不到章节和进度。滚动模式下顶栏还额外压着章节名。

建议（注意不能引入重排）

代码注释明确写了 "Reader content keeps the same geometry whether overlay controls are visible or hidden"——这个决策是对的（避免工具栏显隐触发重新分页），所以修复方案必须保持正文几何不变。

  1. 方案 A（推荐）：把 chapterLabel 移进顶栏作为书名下方的一行副标题（顶栏 48→64dp），把 progressLabel 移进底栏放在 SeekBar 上方。正文区域一行代码都不用改 → 不触发重新分页，冲突自然消失；
  2. 方案 B：给 content 加固定 64dp / 152dp 上下 padding —— 会改变正文高度 → 触发重新分页和页码变化，不可取；
  3. 顺带：底栏已有 SeekBar，章节与百分比信息应该与它成组，而不是散落在正文的上下边缘。
